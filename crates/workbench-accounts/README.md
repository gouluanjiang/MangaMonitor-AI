# Desktop accounts, catalogs, and transient covers

This crate owns authenticated account state and disposable catalog metadata. It never creates library/download jobs or grants authority from local cached content. The existing `login` API saves server sessions only. `login_remembered` adds an explicit JM-only remember-login choice: when both choices are enabled, the validated session and the login password are committed together to the existing protected Windows credential slot. Pica remains token-only. Neither account summaries, catalogs, source sessions, readers nor download plans contain the saved password.

On startup, a saved credential is validated using a session-only copy. Only an explicit `AUTH_REQUIRED` or `SESSION_EXPIRED` from JM, together with a saved opt-in password, permits one fresh login. Transport failures, access denial, rate limits and malformed responses do not trigger password login. Concurrent account reads share the same source lock; normal reads do not repeat a failed fallback. An explicit account refresh may retry it. Success preserves the saved login name and password and atomically replaces the old session only if the credential fingerprint is unchanged. Failures preserve the existing blob. Cancelling remember-login on a successful login saves only the session; cancelling session memory or logging out removes the whole slot. No source operation, favorite write, reader request, scan or download is replayed by this recovery.

`AccountService::query` keeps its forward-order API. `query_ordered` adds a reverse flag passed to the source adapter. Network queries populate an LRU work cache limited to 20,000 records and 32 MiB of serialized metadata per active source session. Entries are evicted individually. Favorite writes require a record loaded by a network query in the current session. Cover-only detail recovery never grants that authority.

`AccountService::catalog` reads and writes snapshots under the verified source/account, folder, and direction. Native account and scope hashes select fixed files in the private app directory. The IPC accepts neither an account key nor a file path. Partial progress retains the last complete snapshot. Older timestamps and conflicting writes at the same timestamp are rejected; identical writes are idempotent. Timestamps must be safe integers no more than five minutes ahead of the native clock.

Each account catalog is limited to 32 MiB and 16 scopes; each snapshot is limited to 20,000 items. The total reservation limit remains 256 MiB and 20 accounts. Whole catalog scopes/accounts may be evicted by recent access. A registry of at most 64 KiB and one temporary file of at most 32 MiB are additional bounded overhead. Failed or oversized catalog writes preserve the old document. Catalogs contain no passwords, tokens, cookies, or session IDs.

Covers are transient. The native cover operation performs source requests and validates a static JPEG of at most 256 KiB and 512 by 512 pixels; it never opens the app-data root or reads/writes cover files. The frontend may reuse images only during the running application. Closing the app discards that reuse. Source requests retain their concurrency and current-session checks; a cover-only recovery never enables favorite writes.

Before publishing its shared document store, the desktop owner retires old disk covers identified by the valid, bounded legacy registry on its first blocking initialization. The cached-store mutex remains held until cleanup finishes, so initial preference and booklist reads cannot race that cleanup. Account listing does not initiate filesystem migration. For each account with a legacy cover reservation, it removes only `cache-{64-lowercase-hex}-covers.json` and `cache-{key}-cover-{000..254}.bin`, then commits that account's zero cover reservation. The fixed old `.cache-transaction.tmp` scratch file is also removed under the same lock. There is no directory enumeration, recursive deletion, or permanent completion marker. A downgraded application that reserves and writes old covers again can be cleaned at the next startup.

Cleanup validates the private directory and every fixed target, rejects symlinks/reparse points and non-file targets, and never deletes catalogs, preferences, booklists, following, credentials, or library content. Missing slots are safe to retry after interruption. Automatic cleanup is attempted once per successfully opened desktop store. Failure does not prevent the store from being published or block document reads, login, or covers. It is not retried on every command. The separate explicit `AccountService::cleanup_legacy_cover_cache` helper retains its result and allows at most three attempts with 100 ms delays on file-lock contention; account listing never invokes it. Unidentifiable files or a damaged registry are conservatively retained; successful cleanup must not be claimed for them. Failed legacy accounts keep their byte reservations and their registry keys until cleanup succeeds.

Tests use synthetic accounts, an in-memory credential vault, tiny generated JPEGs, and temporary directories. They do not contact live services or read real credentials. Compilation and execution for this change are deferred to CI.
