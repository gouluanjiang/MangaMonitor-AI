# 作者作品补全与汉化下载

用户已验收上一批 `481dc1a` 的批量队列、历史整理及跨来源关联。本批按随后讨论确定的作品补全规则开发，取代原来“首次建立时间基线、以后只展示新 ID”的方案。

## 本批功能

- 新增独立“作者作品补全”页面，检查当前 JM、Pica 已认证账号下关注作者的并集；每位作者同时检查两个来源。首次读取会保留旧遗漏，不按扫描日期或入库日期截断。
- 手动开始全部或单个作者检查；逐来源、作者、页顺序读取，展示检查进度和未完成范围。支持停止，已读结果保留；重新打开程序只读取保存的元数据，不自动发起来源检查或下载。
- 关键词搜索命中必须核对作者，缺作者时读取该作品详情；未知命中留在待核对区。总数漂移、跨页重复、分页不完整、限流与会话变化均不被当作“没有遗漏”。每个账号作者上限提高到 1,000；两账号并集最多 2,000。每来源作者范围最多 1,000 页，私有发现文档最多 20,000 条作品、32 MiB。
- 手机存在仍是已入库；电脑存在而手机没有仍是已下载。完整度另行显示：待补入、待传手机、汉化已入库、日文等待汉化、汉化待下载/待替换、待核对等状态。
- 同作品在手机已有任意汉化版本即补齐。只有日文且找到已确认对应的汉化时，在本次显式检查结束后自动将一个汉化版本加入现有电脑下载队列；已有汉化电脑副本则复用。普通遗漏依旧由用户选择下载。
- 提供版本核对：来源编号关联、手机 TXT 名称关联、逐版本语言纠正与撤销。仅名称相似不能自动合并、隐藏遗漏或授权下载。明确来源引用、已有 JM/Pica 关联、用户确认的版本组、完整电脑文件名与手机名单匹配可提供身份依据。语言由明确标签或用户纠正确认，不能仅看是否有汉字。
- 沿用虚拟封面网格与进程内封面缓存；私人目录、手机名单、版本关系和扫描元数据仅保存在本机。没有漫画封面持久缓存。

## 汉化下载与已有链路

用户明确选择“直接下载到电脑，然后由我手动传入手机进行替换”。这授权本地新增汉化副本，不涉及替用户操作手机、删除日文版或覆盖现有目录。手机仍通过手动标记或最新 TXT 更新，电脑副本保留。

自动入队仅来自 native 当前扫描、已核对作者及现有手机/电脑/版本证据。渲染器不提交可自行扩展的下载候选；普通缺失候选没有自动资格。入队及每本开始时核对账号、关注、目录 generation、手机/关联修订与当前资格；图片阶段复用轻量进程检查和已验收的会话约束。换账号、改关注、停止当前检查或开启新的检查会使旧自动资格失效，已有文件保持不变；暂停与后续明确重试沿用队列操作。

检查前核对已知电脑路径，不扫描新文件。只有需要复用的汉化目录会进行定向内容数量/清单核对；不在进度轮询中重复扫描全部漫画目录。真实来源限流/拒绝访问会停止本次继续请求。部分成功的完整度结果只代表已经读到的范围。

## 验证与剩余验收

本地仅编辑、格式化、静态审查、交付工件校验。正式 Rust、Node、Chromium、Windows native IPC、Clippy、Dev 构建和 WebView 启动/重启检查只在既有 GitHub Actions 运行，避免重复执行。合成用例覆盖旧遗漏、中文手机版本、日文到汉化、电脑复用、未知与相似标题、多个来源、手机号/TXT变化、跨页异常、取消和会话漂移、命令权限与只读行为。具体通过数量、最终提交及工件哈希记录在本地交付报告和草稿 PR #19；实现完成不等于真实来源已验收。

真实验收由用户执行：

1. 先选一位已关注作者检查，确认 JM/Pica 范围和旧遗漏；可先关闭汉化自动下载，只核对名单。
2. 用已有手机日文作品，核对对应汉化关系与语言，再开启汉化自动下载并检查该作者；确认仅新增电脑副本、已有原文件保留。
3. 手机已有汉化的作品应列为汉化已入库；电脑已有汉化、手机仅日文的应列为待替换，避免重复下载。
4. 手动传入手机后标记或更新 TXT，刷新入库状态，确认该作品补齐，其他旧遗漏仍在。

仅标题无法判断是否同一作品、来源本身缺失数据、作者别名不一致的情形仍需人工核对；本批不宣称穷尽网站全量内容。继续使用 0.3.4 Dev，无新增安装包。PR #19 保持草稿且不合并，production_enabled=false，应用内更新冻结到正式 V1 后。
