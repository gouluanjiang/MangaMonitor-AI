用户复测上一版 JPG / 两路请求后报告有提速，但仍明显慢于 jmcomic-downloader，并要求采用成熟下载代码。随后明确取消本次下载优化的低电脑负荷限制。本轮接入上游正常的并发结构。2026-09-12，用户在包含删除后重下载修复的整合 Dev 版本 `9e558d2` 上确认“速度显著提升”，本项已完成用户验收。具体秒数和提速倍数未量化；此前单独交付的旧 EXE 不据此补记为单独验收。

## 本轮改动

继续追踪发现另一项直接延迟：桌面下载复用 `JmClient::new` 的监控节奏，每次 `/album`、`/chapter` 请求前随机等待 1–3 秒。单章正常链路涉及一次作品枚举和两次章节读取，仅人为等待就累计 3–9 秒（代码路径推算，不是实测总耗时）。新增仅用于已授权桌面下载的构造路径，这两个接口即时请求；默认构造及其他接口维持原监控节奏。域名、重试次数和请求追踪保持。既有独立 CLI/监控调用不选用此下载路径。

上一版两个请求 future 与图片处理、逐页持久化运行在同一个协调线程。仅提高并发数字无法解决同步解码/编码期间其他 future 得不到轮询的问题。本轮：

1. 图片窗口由 2 调整为 20，每个请求启动独立 Tokio task，网络在协调线程落盘时继续前进。槽位覆盖请求、处理和等待保存的结果，不预取整本图片。
2. WEBP 解码、还原、JPG 编码、最终图像验证和哈希进入 CPU 工作线程。沿用现有 Tokio blocking pool，按可用核心数并行、最多 20；对应上游 async → CPU 工作 → await 的结构，不新增 Rayon 依赖。
3. 已验证输出通过私有不可变值返回，落盘前核对完整描述符（含页号/路径），避免协调线程重复解码同一输出。写后与最终目录检查保留。
4. 电脑目录和下载记录每次仍安全读取完整字节；字节完全相同时复用已验证解析结果。授权读取共享数据，只复制当前任务。变化立即重解析，不能仅凭时间/大小命中，也不增加封面磁盘缓存。
5. 独立跟踪异步任务和实际 CPU 工作。暂停/失败在授权检查点退出后取消剩余请求，等待已派发 CPU 工作结束再释放下载 worker；CPU 工作没有文件写入权限。外层 worker 继续通过授权失效正常退出，不直接丢弃整个执行 future。

直接 JPG 与图片还原已在上一版采用相同算法。GIF 原字节、旧 WEBP 任务和检查点、兼容目录/元数据、手机与电脑状态规则继续保留。仍仅执行一个明确确认的桌面作品，章节按现有顺序衔接；未照搬跨章节/跨作品调度。原来源域、重试、凭据隔离、生产策略不变。

本次采用上游并发/处理结构，保留来源和许可证记录；不是替换整套应用。文件存在即跳过、覆盖旧目标等行为未引入。持久记录与完整性检查仍有成本，因此不能由 2→20 推算十倍提速或宣称已经达到 1–2 秒。
