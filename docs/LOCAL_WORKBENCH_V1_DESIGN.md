托盘常驻和开机自启不属于本轮选择。现有文件无需因新增格式统一为 ZIP 而批量改名、重打包或迁移。

## 文件布局

```text
漫画库/
├─ 作品A.zip
└─ 作品B.zip

作品A.zip 内部：
├─ 第001章/
│  ├─ 001.jpg
│  └─ 002.jpg
└─ 第002章/
   └─ 001.jpg
```

例子用于说明层级；实际章节命名、排序、图片扩展名、文件名字符规范仍需按真实元数据和文件内容实现。作品同名、目标已存在或无法可靠确定目标时进入异常处理，不得把入库解释为允许覆盖。

用户已明确其使用场景中的后续内容作为新漫画作品发布，因此当前范围不做旧 ZIP 追加章节、重打包或版本替换；后续新作品进入发现与批量确认流程。来源记录若出现内容变化则单独标记处理，不自动改写已有压缩包。

## 正常使用流程

1. 用户在详情页确认单本，或在作品列表勾选一批符合条件的作品。
2. “下载并入库”展示本次所选作品和最终保存位置，用户确认一次。
3. 已确认任务进入队列，有空闲名额即开始执行。
4. 后端自动完成源数据与图片获取、来源所需的图片还原、内容验证、一次性 ZIP 保存、最终压缩包验证和安全入库。已取得符合约定的成品 ZIP 时不重复拆包重打；界面不提供图像处理或 ZIP 打包调节项。
5. 验证并更新本地库存，记录当前任务的完成结果，再同步必要状态到 GitHub。
6. 正常任务无需用户逐本进行第二次入库确认。

一次批量确认仅涵盖该次明确选择的任务及其当前目标，不是批准今后发现的所有作品。目标或任务授权发生实质变化时，应暂停受影响任务并明确说明需要重新确认的内容。

自动处理仍执行每一步的证据与状态校验。界面使用作品、保存位置和易懂状态表达意图；任务版本、哈希、回执等技术细节保留在诊断记录中。

## 异常与完成状态

- 重名冲突、磁盘不足、校验失败、身份或授权不确定等任务进入“需要处理”。
- 单本异常不得无故阻塞其他独立且有效的任务。共享磁盘空间不足等共同条件可以暂停受影响范围。
- 短暂网络故障按有界重试与恢复策略处理；不能无限重试或丢弃已有可验证进度。
- 漫画已经入库但云端暂时不可达时，显示“已入库，等待同步”。后续只补同步，不重新下载或再次添加文件。
- 界面区分下载完成、ZIP 校验通过、已入库、等待同步和全部完成，不能用一次下载成功代替整条流程完成。

## 退出与重启

关闭窗口触发协调暂停：停止发起新工作，让无法直接中断的当前写入/提交步骤到达安全边界，持久化任务和恢复信息，再退出。界面应显示保存进度，避免用户误认为窗口卡死。

重启后恢复持久队列，重新核对任务、授权、已有文件和检查点，再继续当前仍有效的已确认任务。不能仅依据“上次正在下载”就信任临时文件；现有下载残留也不能简单删除重来。

上述是必须实现并验证的目标。当前 staging 接口对既有命令目录有严格约束，普通下载器式的断点续传能力尚未完成验收。

## 界面组织：实现起点

- 漫画库：多行封面网格、搜索与筛选，满列后换行并上下滚动；大量封面不采用单行左右滑动。收藏、发现、书单、推荐和搜索等封面列表沿用同一规则，支持多选及既定批量流程。
- 独立作品详情：大封面、标题、作者、来源、简介、章节、本地文件和任务状态；返回时保留列表的筛选与滚动位置。
- 下载队列：显示排队、执行、校验、打包、入库、等待同步和需要处理的任务；暂停、恢复等操作必须对应后端真实能力。
- 发现与复核：展示云端新发现和需要人工判断的关系；未知信息不能显示成确定结论。
- 作者与监控、设置与诊断：作为统一工作台的辅助入口，具体页面划分可在首版界面样例中调整。

“独立详情页”及产品职责已经确认；详情页内部排布、配色、组件样式和信息密度仍是设计建议。

## 技术建议与已有能力

讨论中的技术建议是 Tauri 2 桌面壳、现有 Rust 核心及 React/TypeScript 界面。用户随后授权开始界面样例，`apps/local-workbench` 提供 React/TypeScript 浏览器预览。该样例只验证交互和布局；Tauri 原生壳及真实后端集成仍未交付。

现有后端已有任务复核/批准、执行命令、隔离 staging、校验、add-only 入库、库存更新及精确任务完成模块。还需要实现或补齐：

1. 桌面工作台及统一任务控制器，连接现有模块。
2. ZIP/CBZ 库识别、封面与元数据提取，以及有界缓存。
3. 单作品 ZIP 生成与最终文件验证；入库及库存证据要绑定实际 ZIP 与其内部内容。
4. 可持久化队列、安全退出与恢复，及入库/回执丢失后的精确重试。
5. 本地库存与任务完成结果的可靠云端发布和冲突处理（Issue #7）。
6. 首次完整库存建立、可信新作依据，以及一项真实获批新任务的端到端验收。

现有入库策略只绑定一份精确 staging 结果，当前仍关闭；自动批量入库需要实现逐任务的授权衔接。现有 importer 使用命令目录及完成标记保存媒体，改为作品名 ZIP 需要贯通最终压缩包、复扫、库存和任务完成证据，不能只修改文件名。

实际媒体、入库及完成逻辑的实现仍遵循 `AGENTS.md` 与其引用的执行契约。产品交互确认不代表生产已经启用、真实任务已经获批，或现有 materialization policy 已自动改变。
