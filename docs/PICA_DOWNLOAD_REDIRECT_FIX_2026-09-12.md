# Pica 单本下载：图片跳转修复

## 原因与证据

用户的真实验收停在目录枚举完成、图片尚未保存的阶段，界面只有通用失败提示。本轮只读检查了这一本失败任务及第一页图片元数据，并针对首张图片核对 HTTP 响应头；没有启动下载任务、读取图片正文或修改漫画库。

来源返回的 `fileServer` 为已经受支持的 `storage-b.picacomic.com`。初始 `/static/tobs/...jpg` 在 HEAD 和 GET 下均返回 HTTP 301，Location 指向同一 HTTPS origin 的另一个 `/static/...jpg` 地址，随后返回 HTTP 200、`image/jpeg`。本例不属于未受支持的 CDN，也没有证据说明来源图片损坏。

项目真实下载 transport 关闭了自动跳转，并把任何非 200 响应作为失败；桌面错误分类又把 `PICA_MEDIA_HTTP_301` 压成 `DOWNLOAD_FAILED`。这是本项目的兼容缺口。上一批合成测试覆盖了分页、图片处理、保存和登记，但未覆盖图片服务器返回 301 的真实请求流程，因此 CI 通过没有发现该问题。

## 修复范围

- 桌面 Pica 下载手动处理 HTTP 301/302/303/307/308，最多两次跳转；只接受原始已审计 HTTPS origin 内的 `/static/` 地址。拒绝跨来源主机、登录信息、查询、fragment、路径变形、循环和超限链。HTTP client 的自动跳转仍关闭，不猜测替代路径，不增加失败重试。
- 初次 GET 和每次跳转 GET 都向当前暂存协调器请求一次新的任务/批准/会话检查。HTTP 工作线程只持有内部通道，不能缓存批准或访问会话凭据。暂停、会话变化、代次不符及关闭会阻止后续请求；已派发任务沿用现有取消和等待退出机制。
- 每一跳实际请求与响应 URL 必须一致。来源描述符、暂存路径和 checkpoint 仍绑定 API 返回的原始媒体 URL；跳转不会改写描述符或使历史重试进度失效。最终图片继续通过原有解码、格式、哈希、完整文件清单和电脑登记检查。
- 下载错误区分图片连接/超时、跳转异常、访问拒绝、限流、来源响应、空图片和图片解码失败。队列仍只保存固定错误码，界面不显示原始响应、媒体 URL 或凭据。

JM、旧的非续接执行入口、下载并发、图片格式及手机入库规则保持原有行为。生产仍 disabled，不新增覆盖、替换、删除或安装更新权限。本例没有要求扩大媒体主机白名单，其他 CDN 兼容性不能据此宣称全部通过。
