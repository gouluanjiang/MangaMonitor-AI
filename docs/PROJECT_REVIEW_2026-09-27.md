## 1. [P2] 清理完成历史后，同路径替换文件会造成错误入库身份

主要位置：[presence.rs:71](../crates/workbench-downloads/src/presence.rs#L71)。

**触发过程：**下载作品 A 并入库 → 清理 A 的完成历史 → 在文件管理器中删除 A，把另一份合法 ZIP B 放到原文件名 → 重新读取漫画库 → 查看来源中的 A。

**实际后果：**A 仍会显示“已入库”，来源详情的下载按钮被禁用；“查看电脑文件”指向 B。无需让 B 与 A 大小相等，也无需伪造 B 的元数据。

**原因与依据：**

- `service.rs:612–620` 清理历史时只保留来源、作品编号、根目录、目标路径和库条目 ID，没有保存原文件身份。
- `workbench-library/src/scan.rs:161` 按根目录与相对路径生成条目 ID，因此 B 沿用该 ID；扫描会正确记录 B 的新文件身份，也只在身份相同时保留旧关联。
- `inventory.rs:73–86` 用旧历史的 A 编号输出状态，却把当前扫描的 B 交给 `check_history`。
- `presence.rs:71–77` 使用当前库记录的身份作为期望值，之后自然验证 B 与 B 相等，返回 `Present`。
- 前端 `inventory-model.ts:45–53` 接受该状态；`SourceWorkbench.tsx:1567–1594` 据此显示已入库并禁用下载。

**建议修复：**清理历史时保留能约束原文件的身份凭据；重扫不能把新文件的身份当成原下载证明。旧格式历史若无法证明同一文件，应返回待核实，而不是自动确认归属。不需要恢复标题猜测或跨站自动匹配。

**缺失回归：**现有历史测试在删除／替换后直接读取 inventory，未覆盖“合法 ZIP 替换 → 完成重扫 → 再读取 inventory”。需要验证 A 不再被标记为已入库，B 的正常读取不受影响。

**验证级别：**已交叉核对原生调用链、文件身份、扫描和前端消费逻辑；没有操作真实漫画或执行原生复现测试。

## 2. [P2] 搜索期间网站分页总量变化，仍可能错误宣称读取完整

主要位置：[source-search.ts:182](../apps/local-workbench/src/source-search.ts#L182)。

**触发过程：**读取第 1 页时网站有 40 条；随后网站删除第 1 页的一条，剩余结果前移；第 2 页报告 39 条。

**合成诊断实际结果：**第 1 页得到编号 1–20；第 2 页得到 22–40。搜索最终标记 `run=complete`、`pagesComplete=true`、共 39 条，却遗漏仍存在的 21，并保留已删除的 1。

**原因与影响：**`readCompleteSearch` 检查当前页的总数是否与累计数矛盾，但没有比较相邻页 `total/pages` 是否变化。累计 39 恰好等于新总数，因而通过完整判断。作者搜索和普通关键词搜索均复用这段逻辑；作者页可能显示“当前检查范围已读完”，若所有返回项已入库，还可能误报本次作者作品全部入库。此结论针对临时搜索，不是说已有后端增量目录同样缺少检查。

**建议修复：**保存每个查询的分页基准，在总量／页数变化时保留已读内容并明确标记本次范围未完成；续读也携带该基准。可复用后端 `discovery.rs` 已有的跨页一致性思路。仅凭总量稳定仍无法保证网站在同总量换入换出时提供快照一致性，不应扩大完整性承诺。

**缺失回归：**现有测试覆盖固定总量、短页、重复页和网络失败，缺少上述“总量缩小且累计刚好相等”的场景。

**验证级别：**已用纯内存合成来源直接运行现有 `createAuthorSearchAdapter` 和 `validateSourcePage`，得到 `bugReproduced=true`。没有网络、IPC、账号或真实书目。

## 3. [P2] 纵向阅读的短尾页无法自然触发章节结束提示

主要位置：[ReaderSession.tsx:571](../apps/local-workbench/src/reader/ReaderSession.tsx#L571)。

**触发过程：**纵向阅读中，最后一张图片加间距的高度小于视口，滚动到底。手机小窗、横图或缩小显示均可能遇到。

**实际后果：**尾页能够看到，但“本章已到最后一页／下一章”不出现，页码也可能停在倒数第二页。章节选择器和单页阅读仍可使用，因此不是完全无法阅读尾页或进入下一章。

**原因与依据：**当前页取视口顶部所在图片，而 `atEnd` 额外要求该图片必须是末页。最后一张较短时，最大滚动位置的顶部仍落在前一页，条件始终不成立。

直接调用现有布局函数得到：视口 390×844，三页高宽比为 1.45、1.45、1；内容高 1557，底部 `scrollTop=713`，当前页索引 1，`actualBottom=true`，但 `atEnd=false`。

**建议修复：**纵向模式依据实际章节末端是否进入视口判断章末，并协调底部页码与进度条；单页模式保留末页索引判断。增加窄窗口、短尾图和缩小显示的回归。

**缺失回归：**现有章节末尾浏览器测试使用比视口高的图片并先跳到末页，未覆盖自然滚动到短尾页。

**验证级别：**已运行现有 `pageLayout` 和 `pageAtOffset` 的隔离几何诊断；本轮没有重新接管真实阅读窗口。

## 4. [P2] 同批下载的输出文件名冲突没有在确认前发现

主要位置：[service.rs:1252](../crates/workbench-downloads/src/service.rs#L1252)。

**触发过程：**两部不同编号作品经过现有作者／标题命名规则后得到相同 ZIP 文件名；目标文件尚不存在，将两部同时加入确认队列。

**实际后果：**两项均通过确认。第一部保存后，第二部仍读取媒体、校验并构建 ZIP，直到创建最终文件才报 `DOWNLOAD_FILE_EXISTS`；按原任务重试仍遇到相同目标冲突。最终使用 `create_new`，不会覆盖第一部，问题是可预见的无效下载与无法靠普通重试解除的失败。

**原因与依据：**`confirm_prepared` 会逐个将候选写入临时任务集合，但 `check_new_download` 遍历任务时先按来源＋作品编号过滤，没有比较其他编号已预留的目标文件名。文件系统检查此时也看不到尚未生成的目标。实际创建位于 `materialize/archive_output.rs:180`，在媒体处理和 ZIP 构建之后。

**建议修复：**确认前同时检测同批和现有待处理任务的目标路径冲突，遵循 Windows 文件名比较规则，给出具体冲突项；执行前再检查目标是否已出现。是否提供新文件名应由明确命名方案决定，不能覆盖现有文件，也不能直接把同名作品当成同一本。

**缺失回归：**批量下载测试给不同编号生成不同标题，未覆盖不同编号／来源归一化为同名的情形。

**验证级别：**静态核对确认、执行、保存与排他创建的完整调用链；未执行下载复现。
